# H100 较大矩阵通算融合实测

## 第十二课大矩阵性能对比

H100 实测结果：当前单 Kernel 通算融合实现，在较大的 Expert MLP 上没有取得性能优势。同一 NVSHMEM 后端、同一 CUTLASS 计算和缓冲区下，融合与分离的延迟接近；NCCL＋PyTorch CUDA GEMM 的分离路径明显更快。

### 对比实现与输入

每个 GPU 对应一个 EP Rank 和一个 Expert，E=P，使用 FP16 输入和权重、FP32 矩阵累加。Expert 执行 Up Projection → GELU → Down Projection，最后以 FP32 按 1/K 加权合并。以下 N 为每 Rank 的原始 Token 数，H 为 Hidden Size，F 为 Expert Hidden Size。均匀 Top-2 路由下，每个 Expert 共收到 2N 行，Up 的矩阵形状为 [2N,H] × [H,F]，Down 为 [2N,F] × [F,H]。

融合路径的 `fused_mlp()` 在同一个 Kernel 内完成 Token 发送、输入就绪等待、两次矩阵投影与 GELU、结果回传。`combine()` 独立恢复原 Token 顺序，因此完整测量区间有两个 Kernel。分离对照依次启动发送、Up＋GELU、Down、回传、Combine，共五个 Kernel。两者调用完全相同的 NVSHMEM block 通信 API 和 CUTLASS GEMM，使用相同权重、128 个计算 CTA、Tile 分配、工作区与加权合并；融合路径另有一个通信控制 CTA。

计算复用 CUTLASS 3.9.2 的 GEMM 主循环与 Epilogue，采用 SM80 Tensor Core 兼容路径、64×64×32 Threadblock Tile、32×32×32 Warp Tile 和两级主循环。Up Epilogue 先将累加值舍入到 FP16，再计算 GELU，与 PyTorch 的 FP16 中间 Tensor 边界对应。H 和 F 需为 8 的倍数，Token 行数支持尾块。该配置在 H100 上真实执行，使用 FP32 Reference 独立核对。

NCCL 对照使用 `all_to_all_single()`、PyTorch 的两次矩阵乘法和 GELU，再进行 Return A2A 与 FP32 Combine。它把收到的 Token 紧凑地合成一个本地 Expert Batch；NVSHMEM 路径以来源 Rank 分块保存数据。NCCL 对照提供实际使用中的整条路径性能；融合本身的影响由共用 NVSHMEM 与 CUTLASS 的两条路径衡量。

### 测量范围

计时从准备好的 Rank-packed Token 开始，到原 Token 顺序的 FP32 加权输出结束，包含两次通信、Expert MLP 和 Combine。Router、打包、计数交换、初始化、编译和 Host 结果拷贝位于计时区间之外。NVSHMEM 使用预分配缓冲区；PyTorch 的中间 Tensor 分配包含在其执行区间中。

GPU 使用 CUDA Event 计时，每个样本先取最慢 Rank，再报告中位数及 P10～P90。NVSHMEM 按融合、分离、分离、融合的顺序分四组，每组预热 10 次、测量 30 次，每种实现共 60 个有效样本。NCCL 分两组，每组同样预热 10 次、测量 30 次。每轮计时前的 MPI/NCCL barrier 与上一轮同步均位于计时区间外。

运行环境为 H100 80GB、CUDA 13.2、PyTorch 2.12.0a0、NCCL 2.29.7、NVSHMEM 3.6.5、CUTLASS 3.9.2。同节点 GPU 通过 NVLink 连接；2 卡使用物理 GPU 6、7，4 卡使用 2、3、6、7。容器配额为 4 CPU、16 GiB 内存。GPU 为共享环境，启动前其他进程已有显存分配，采样时利用率为 0%；本次数据对应这组环境。完整 GPU 清单、拓扑和运行参数随附件提供。

H=4096、F=14336 时，2 卡、N=512 的单 Kernel 路径为 7.2387 ms，NCCL 路径为 0.4942 ms；N=1024 时分别为 14.5529 ms 与 0.8650 ms。4 卡、N=512 时分别为 7.8636 ms 与 0.5724 ms。三个配置下，NCCL 路径快约 13.7～16.8 倍。同后端分离分别为 7.1432、14.3690、7.8165 ms，融合的中位数略慢 0.6%～1.3%。

小规模对照中，2 卡 N=17、H=136、F=264、Top-1 的融合与同后端分离分别为 0.0361、0.0389 ms，差约 2.85 μs。随着矩阵扩大，通信和 GEMM 的耗时增长，减少三次 Kernel 启动带来的收益占比随之下降。

### 时间线与耗时构成

Nsight Systems 对 2 卡、N=512、H=4096、F=14336 单独采集时间线。每个 PE 记录到 10 次 `fused_mlp()`、20 次 `combine()`、20 次 `exchange()` 和 20 次 `projection()`，与两条路径各 10 轮的执行结构一致。初始化及计时外的 NVSHMEM barrier Kernel 单独保留在 Trace 中。

|PE|分离路径每轮两次通信 GPU 时间|每轮两次投影 GPU 时间|每次 Combine GPU 时间|融合主体 GPU 时间|
|---|---:|---:|---:|---:|
|0|3.2438|3.8776|0.0124|7.2350|
|1|3.2933|3.9044|0.0124|7.2714|

这些时间来自带采集开销的 Trace，表中的阶段值用于解释耗时构成，性能表使用独立的无 Profiler 测量。以 PE 1 为例，两次通信合计约 3.29 ms，两次投影约 3.90 ms，两项合计已接近融合主体的 7.27 ms。

当前实现由一个 CTA 推进 NVSHMEM 通信，计算 CTA 复用上述 CUTLASS Tile；通信完成后才进入 Up，整个 Up 完成后进入 Down，Down 完成后回传。阶段之间使用 Cooperative Grid 同步。融合减少了 Host 发起 Kernel 的次数，同时保留了通信量、全局内存中的中间激活以及阶段依赖。这组结果说明，当前实现的主要优化空间在通信吞吐、GEMM 执行和按数据就绪推进计算；仅合并 Kernel 启动，带来的收益很小。

### 正确性与复现

共完成 14 个配置、40 个 Rank/配置检查，覆盖 EP=2/4、Top-1/2、均匀与倾斜路由、空 Expert，以及 N=17 的 Token 尾块。融合和同后端分离输出逐元素相同；两者与独立 FP32 GEMM Reference、NCCL 输出均通过 atol=0.003、rtol=0.02 的比较。独立 Reference 在 Up、GELU 和 Down 边界显式恢复 FP16 舍入，最终 Combine 为 FP32。

所有配置中最大的绝对误差为 0.00024414。send/recv 行数与路由恢复关系一起核对，输出的 shape、dtype 和 device 也已检查。各 Rank 的最慢 Rank 样本数组逐项一致。H100 源码 SHA256 与本地交付源码一致。

完整实测命令在附件的 `compile-final.sh`、`cutlass-sweep.sh`、`profile.sh` 中；程序入口为 `mini_ep/kernels/nvshmem/large_expert.cu` 和 `benchmarks/benchmark_large_fusion.py`。C++ 程序生成原始 Token、权重、路由及结果，Python 程序读取同一输入进行独立核对和 NCCL 测量。二进制输入可按源码中的随机种子 20261007＋Rank 重新生成，附件提供其 SHA256。

本次未执行独占 GPU 复测、跨节点测试、BF16 对照、Hopper WGMMA/TMA 专用 GEMM，以及按 Chunk 交错推进的单 Kernel 流水线。结果对应当前两个实现与上述计时范围。

### 实现依据

CUTLASS 的 GEMM Kernel 与 Epilogue 源码为计算组件依据；NVSHMEM Collective Launch 使用 CUDA Cooperative Launch，Grid 大小通过查询接口限制；block 版 put-with-signal 由整个 CTA 参与。接口依据：[CUTLASS 3.9.2 GEMM](https://github.com/NVIDIA/cutlass/blob/v3.9.2/include/cutlass/gemm/kernel/gemm.h)、[NVSHMEM Kernel Launch](https://docs.nvidia.com/nvshmem/api/latest/api/launch.html)、[NVSHMEM Signaling Operations](https://docs.nvidia.com/nvshmem/api/latest/gen/api/signal.html)。
