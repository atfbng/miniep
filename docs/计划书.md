# 三、课程的核心技术路线

本课程明确采用：

> **All-to-All Expert Parallel**

作为主线。

不是通过：

```text
AllGather + Tensor Parallel
```

来模拟 EP。

核心原因是 Expert Parallel 的本质是：

> Router 决定 Token 应该由哪个 Expert 处理，而不同 Expert 分布在不同 GPU，因此必须进行 Token Redistribution。

对应最自然的通信模式就是：

```text
All-to-All
```

完整的数据流：

```text
Input Tokens
      ↓
Router
      ↓
Top-K Expert Selection
      ↓
Expert → Rank Mapping
      ↓
Token Count / Histogram
      ↓
Token Permute / Dispatch
      ↓
Pack by Destination Rank
      ↓
NCCL All-to-All #1
      ↓
Local Expert Tokens
      ↓
Grouped GEMM / Expert MLP
      ↓
NCCL All-to-All #2
      ↓
Token Unpermute
      ↓
Routing Weight Combine
      ↓
Output Tokens
```

# 四、EP 与 TP 的课程边界

课程必须让学生明确：

## Expert Parallel

核心思想：

```text
不同 Expert
放在不同 GPU
```

例如：

```text
GPU0 → E0 E1
GPU1 → E2 E3
GPU2 → E4 E5
GPU3 → E6 E7
```

核心通信：

```text
All-to-All
```

---

## Tensor Parallel

核心思想：

```text
同一个矩阵 / Expert
被多个 GPU 切分
```

例如：

```text
W = [W0 | W1]
```

常见通信：

```text
AllGather
ReduceScatter
AllReduce
```

---

## 本课程安排

主课程：

```text
Pure Expert Parallel
+
All-to-All
```

高阶扩展：

```text
TP × EP
```

因此：

```text
EP → 主课程

TP × EP → 可选扩展课程
```

# 十二、通信设计

课程第一阶段统一使用：

```python
torch.distributed.all_to_all_single()
```

底层 Backend：

```python
dist.init_process_group(
    backend="nccl"
)
```

调用关系：

```text
Mini-EP Python
↓
torch.distributed
↓
ProcessGroupNCCL
↓
NCCL
↓
PCIe / NVLink / Network
↓
GPU
```

课程：

**需要理解 NCCL**

但：

**不要求自己重新实现 NCCL。**

第 12 课增加设备侧通信后端。基础 EP 和 Stream 路线继续使用 `torch.distributed` 与 NCCL；Kernel 路线通过 NVSHMEM 的设备侧 API 完成远端 Token 数据传输，保持相同的 Expert 放置、路由分支和输出恢复语义。

该后端使用 PE（Processing Element，NVSHMEM 通信参与进程）标识目标，明确 EP rank、PE 与 GPU 的映射。接收区和信号区采用 NVSHMEM 对称内存，各 PE 按一致的分配顺序建立通信对象。变长数据通过行数、偏移与容量 metadata 定位，协议同时定义数据到达、消费完成和缓冲区复用条件。接口依据 [NVSHMEM 概述](https://docs.nvidia.com/nvshmem/api/latest/introduction.html)与[内存管理文档](https://docs.nvidia.com/nvshmem/api/latest/gen/api/memory.html)。

```text
Unpermute
+

+
```

## Kernel 内通信与计算

从 EP=2 的最小例子开始：两个 PE 各持有一批 Token 和本地 Expert。Host 预先完成路由、目标偏移与对称缓冲区分配，并在每个 PE 上启动通信计算 Kernel。Kernel 将本地发送块写入目标 PE 的接收区；接收方确认对应信号后，直接读取该块并执行计算，再把结果送回原始 PE。Host 在 Kernel 完成后恢复原 Token 顺序，应用路由权重并合并 Top-K 分支。

首个例子采用可逐元素对照的缩放或小矩阵计算，建立通信协议和数据顺序。随后把计算阶段替换为设备内可执行的 Expert 分块 GEMM 与激活，复用成熟的 CUDA/CUTLASS 计算组件。主机侧 cuBLAS 调用保留在 Stream Reference 路线，Kernel 路线采用设备侧计算组件。

同一 Kernel 内的基本数据流为：

```text
发布本地发送块
↓
写入远端接收区，并发布该块的就绪信号
↓
等待本地所需块就绪
↓
读取 Token，执行本地计算
↓
发送结果，并发布返回信号
↓
确认最后一次访问完成，结束当前轮次
```

阶段建立后，再将工作分成 Tile 或 Chunk，为通信和计算分配明确的线程块或 Warp 角色：一部分工作准备与传输后续块，另一部分工作消费已就绪块。逐块就绪后的串行消费用于验证基础协议；细粒度重叠通过后续流水线实验测量。

### 数据接口与通信协议

接口需要写清原始 Token `[T,H]`、展开后的分支 `[T*K,H]`、目标 PE 顺序的发送缓冲区，以及来源 PE 分块的接收缓冲区。行数、偏移和恢复索引采用明确的整数类型；输入、Expert 权重和输出注明 FP32/FP16/BF16、device、stride 与连续性条件。通信容量按每轮实际行数或约定的最大行数分配，所有 PE 的分配尺寸与布局满足对称内存契约。

每个发送块对应独立的目的地址和就绪信号。可采用 `nvshmem_putmem_signal` 将一段连续数据及其完成通知关联起来，接收端通过对应的 signal wait/test API 判断何时可以读取这段数据。独立传输之间的顺序、非阻塞发送源缓冲区的复用条件，以及 `quiet`/`fence` 的作用，按所用 API 的完成与内存顺序语义分别定义。依据 [Signaling Operations](https://docs.nvidia.com/nvshmem/api/latest/gen/api/signal.html)与[Memory Ordering](https://docs.nvidia.com/nvshmem/api/latest/gen/api/ordering.html)。

信号使用轮次编号，并明确 `(source_pe, chunk_id, slot)` 对应关系。复用接收槽前，生产者需要得到上一轮消费完成的确认；返回缓冲区也遵守相同的生命周期。空块明确规定是否发送通知，各 PE 采用一致的协议。循环末尾完成最后一批数据消费与返回，随后再允许 Host 读取结果、重置状态或释放对称内存。

### 启动、同步与通信进展

含 NVSHMEM 同步或 collective API 的 Kernel 使用 `nvshmemx_collective_launch` 启动，并根据查询结果设置允许的 grid 大小。协议检查跨 PE 和跨线程块的等待依赖，保证负责发送或发布信号的工作能够获得执行资源。Warp/Block 级通信 API 的参与线程满足各自的调用约定；消费线程读取数据前，还要建立相应的本地线程同步。依据 [Kernel Launch Routines](https://docs.nvidia.com/nvshmem/api/latest/api/launch.html)与[NVSHMEM and the CUDA Model](https://docs.nvidia.com/nvshmem/api/latest/cuda-interactions.html)。

实验环境采用一 PE 对应一 GPU，并为该路线安排独占 GPU 时段。先使用同节点、可用 P2P 的 H100 配置，记录 NVLink/PCIe 拓扑与实际传输方式；跨节点通信再补充网络和传输后端配置。NVSHMEM 初始化、对称内存分配与 Kernel 启动遵守所用版本的执行要求，参见 [Using NVSHMEM](https://docs.nvidia.com/nvshmem/api/latest/using.html)。

### Kernel 路线验收

正确性覆盖 EP=2、条件允许时 EP=4，Top-1/Top-2，空 Expert、零长度通信块、非均匀路由、多轮循环和双缓冲复用。结果与同步 NCCL EP Reference 比较，检查值、shape、dtype、device、返回顺序、计数与恢复索引。等待设置可诊断的超时机制，记录 PE、轮次、Chunk 与预期信号，验证失败时让全部参与进程退出。

性能比较包含同步 NCCL EP、Stream Pipeline 与 Kernel 内通信计算。保持输入、Expert 数、路由、dtype 与测量范围一致，分别报告端到端最慢 Rank/PE 延迟、Tokens/s、启动数量、通信字节和协议等待成本。小规模教学计算与实际 Expert GEMM 分别报告，记录 Tile/Chunk 大小及计算实现。

Nsight Systems 用于观察 Host 提交、Kernel 启动和整层完成时间；Kernel 内通信、等待与计算阶段增加可选的设备侧时间戳或轻量计数，并单独测量采样开销。联合 Nsight Compute 或适用的设备侧通信工具分析资源占用与进展。每条“发生重叠”或“降低延迟”的结论都对应测量证据，明确重叠区间与统计口径。

# 二十九、课程最终要求学生回答的问题

Kernel 路线追加四个问题：设备侧远端写入怎样通知消费者；信号轮次怎样防止读取旧数据；通信与计算线程怎样获得足够的执行资源；怎样结合端到端 Timeline 和 Kernel 内测量确认性能变化的来源。

### Q1

为什么 MoE EP 使用 All-to-All，而不是简单 AllGather？

### Q2

为什么 EP=4 不一定比 EP=2 快？

### Q3

什么时候 EP 是 Communication Bound？

### Q4

什么时候 Expert Compute 是主要瓶颈？

### Q5

为什么 Expert Load Imbalance 会降低整体 GPU 利用率？

### Q6

Grouped GEMM 为什么适合 MoE？

### Q7

为什么 Triton Dispatch 能比多个 PyTorch 操作更快？

### Q8

Kernel Fusion 主要减少了什么？

### Q9

为什么：

```text
async_op=True
```

不等于一定发生 Communication / Computation Overlap？

### Q10

为什么 Chunking 是形成 Pipeline 的关键？

### Q11

Chunk 越小是否一定越好？

答案应该认识到：

```text
chunk 越小
→ pipeline 粒度更细

但同时

→ NCCL launch 增多
→ kernel launch 增多
→ synchronization 增多
→ bandwidth utilization 可能下降
```

因此需要 Benchmark 找最佳点。
